# Alfred shared memory — manual test plan

Feature under test: the shared memory engine added to Alfred (`src/memory/`, `hooks/alfred-hook.js`,
`src/integrations/memoryHooks.js`, `src/commands/memory.js`, `knowledge/alfred-core.md`), wired into
Claude Code, GitHub Copilot and Codex via `alfred sync`. Built by Codex (astra 6). Automated
`npm test` already passes; this plan is for exercising the same behavior by hand, in the actual
CLI and VS Code surfaces of all three tools, per the implementation notes in
`docs/memory-implementation.md` and `README.md` ("Shared memory" section).

Repo under test in this plan: `E:\code_with_santan\Alfred-2.0\Alfred` — adjust the path if your
clone lives elsewhere. Commands are given for PowerShell; a Git Bash equivalent is noted where it
differs.

> This is a document, written in plain English on purpose — read it like a runbook, not a chat reply.

---

## 0. What "pass" means

Per the implementation notes, this feature has two kinds of proof:

- **Code-level proof** (already done): `npm test`, `alfred sync` twice, generated file contents.
  You are re-verifying this by hand in sections 1–5.
- **Live host proof** (not yet done as of this writing): an actual skill invocation inside each
  tool's CLI and VS Code surface, where the model itself runs the generated startup step or a
  native hook fires, and memory files change as a result. Sections 6–8 are this.

Do not mark a tool "done" from console output alone — confirm the `.alfred/` files in the test
project actually changed timestamps/content after a real skill run in that host.

## 4. Manual CLI test of the memory engine itself (tool-agnostic)

This exercises `src/memory/engine.js` directly through `alfred memory`, without needing any AI
tool to actually run — useful to isolate "the engine works" from "the host wired it up right."

From your test project directory:

```powershell
cd "E:\code_with_santan\Alfred-2.0\memory-test-project"
alfred memory start --skill pr-code-review --tool codex
```

- [ ] `.alfred\` folder is created in the test project, containing `.gitignore` (`*`), `README.md`,
      `memory.md`, and empty `sessions/`, `feedback/`, `.state/` folders.
- [ ] Console prints a receipt block starting `Alfred memory ready: pr-code-review`, a `Tool:
      codex; session: <uuid>` line, then `## Alfred core rules`, `## Global facts`, `## Project
      facts`, `## Skill improvements` sections (this is the "first call in this session" path).
- [ ] `.alfred\feedback\pr-code-review.md` now exists with `uses: 1` and today's date on `last:`.
- [ ] `.alfred\sessions\` has one new file named like
      `2026-09-12T...-codex-<24 hex chars>.md`, with a `skills: pr-code-review` line.

Copy the session UUID printed above, then re-run using it explicitly and add a second skill:

```powershell
alfred memory start --skill ship-pr --tool codex --session <uuid-from-above>
```

- [ ] Output is shorter this time: no core rules/global/project facts, just the receipt,
      `Alfred rules already loaded...` line, and `## Skill improvements`. This is the "not first
      call" path — same session ID, second skill.
- [ ] The **same** session file's `skills:` line now reads `skills: pr-code-review, ship-pr`.
- [ ] `.alfred\feedback\ship-pr.md` was created with `uses: 1`.

End the session:

```powershell
alfred memory end --tool codex --session <uuid-from-above>
```

- [ ] No console output (silent success). The `.alfred\.state\<hash>.json` file for that session
      is deleted. The session `.md` file under `sessions/` remains (history isn't deleted on end,
      only the live bookkeeping is — pruning of stale/empty sessions happens on the next `start`).

### 4.1 Retry / duplicate-event idempotency

```powershell
alfred memory start --skill ship-pr --tool codex --event try-1
alfred memory start --skill ship-pr --tool codex --session <same-session-id> --event try-1
```

- [ ] Check `.alfred\feedback\ship-pr.md` — `uses` incremented only **once** across both calls,
      because the second call reuses the same `--event` ID (simulates a hook retry).

### 4.2 `--refresh` after a simulated compaction

```powershell
alfred memory start --skill ship-pr --tool codex --session <session-id> --refresh
```

- [ ] Output goes back to the "full" form (core rules + global + project facts), even though this
      session already existed — confirms `--refresh` forces a reload after context compaction.

### 4.3 Opt-outs

**Environment variable:**

```powershell

alfred memory start --skill ship-pr --tool codex

```

- [ ] Output is exactly: `Alfred memory inactive (opt-out, unknown skill, or excluded workspace).
      Continue the skill normally.` No `.alfred` writes happen (check no new session file was
      added).

**Per-workspace config:**

```powershell

alfred memory start --skill ship-pr --tool codex
```

- [ ] Same inactive message as above. Then remove/reset the file:
      `Remove-Item "E:\code_with_santan\Alfred-2.0\memory-test-project\.alfred\config.json"`.

**Per-skill frontmatter (`memory: false`):**

1. In the Alfred repo, temporarily add `memory: false` to one skill's frontmatter, e.g.
   `skills\writing\santan-voice.md`:
   ```yaml
   ---
   name: santan-voice
   description: ...
   memory: false
   ---
   ```
2. Re-run `alfred sync` (or at least `alfred build`).
3. Check `plugin\santan-voice\santan-voice.md` — **no** `## Alfred memory startup` block was
   injected this time.
4. Check `config\skills-index.json` — the `santan-voice` entry now shows `"memory": false`.
5. From the test project: `alfred memory start --skill santan-voice --tool claude` → same
   inactive message (engine refuses because the skill is memory-disabled).
6. **Revert** the frontmatter change and re-run `alfred sync` before moving on, so you don't leave
   the repo in a modified state.

### 4.4 Context caps / truncation

Global cap is 20 lines / 1100 chars; project cap is 40 lines / 2200 chars (see `DEFAULTS` in
`src/memory/engine.js`, and `README.md`'s cap table).

```powershell
$lines = 1..50 | ForEach-Object { "- [test] 2026-09-12 filler fact number $_" }
$lines -join "`n" | Add-Content "E:\code_with_santan\Alfred-2.0\memory-test-project\.alfred\memory.md"
alfred memory start --skill pr-code-review --tool claude --refresh
```

- [ ] `## Project facts` in the output shows only the first 40 lines and ends with
      `[Memory capped; consolidate dated facts in place.]`.
- [ ] The **file on disk** still has all 50 lines — capping only affects what's injected into
      context, never what's stored (per the "never silently truncated on disk" guarantee in
      `README.md`).
- [ ] Clean up: trim `.alfred\memory.md` back down, or just delete the test project and recreate
      it before the live-host tests below.

### 4.5 Concurrency (file lock)

Run two starts back to back against the same session with no gap, to sanity check the
`.alfred/.state/write.lock` mechanism doesn't corrupt counters:

```powershell
$job1 = Start-Job { alfred memory start --skill pr-code-review --tool claude --session concurrenttest }
$job2 = Start-Job { alfred memory start --skill pr-code-review --tool claude --session concurrenttest }
Receive-Job $job1, $job2 -Wait
```

- [ ] Both jobs complete without throwing `Memory is busy; retry shortly` under normal timing
      (lock is held only for the duration of one file write). `.alfred\feedback\pr-code-review.md`
      `uses` increased by exactly 2, not corrupted or overwritten.
